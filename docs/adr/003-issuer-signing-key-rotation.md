# ADR-003: 발급 키 교체와 과거 토큰 검증 키의 수명을 분리한다

## Status

Accepted — 정책 및 구현 설계 결정 (2026-10-15). 런타임은 선택적인 키 묶음 모드를
지원한다. 운영 키 이관·전환과 소비자 검증은 별도 단계다.

## Context

AuthGate는 access/ID token을 발급하고, 자체 UserInfo·introspection과
authorize·logout에서 토큰을 검증한다. 기존 단일 RSA 키와 고정 `kid`는 안전한
교체를 지원하지 않는다. 키 파일만 바꾸면 기존 토큰 검증과 소비자 캐시가 깨진다.

만료 전 JWT의 수명은 유한하지만, 현재 허용하는 만료된 `id_token_hint`에는
추가 보존 기간의 상한이 없다. 같은 공개 키 목록 하나로 모든 용도를 처리하면
일반 JWKS에서 구 키를 제거하는 시점도 정할 수 없다.

## Decision

- 발급용 개인 키는 프로세스마다 하나다. 서명 키와 검증용 공개 키 목록을 하나의
  버전 있는 묶음으로 시작 시 검증하고, 프로세스 수명 동안 변경하지 않는다.
  운영자는 사전 공개·활성화·공개 종료를 별도 배포로 진행한다.
- 새 키에는 키 재료에 결합된 고유 `kid`를 사용한다. 기존 키를 새 형식으로
  옮기는 첫 단계에서는 기존 `authgate-key-1`과 키 재료를 함께 유지한다.
  같은 `kid`에 다른 공개 키를 배정하지 않는다.
- 모든 발급자에서 새 공개 키를 먼저 제공하고, 소비자의 새 키 수용을 검증한 뒤
  서명 키를 바꾼다. Secret 반영, 재시작 또는 정해진 대기 시간만으로 이 게이트를
  통과한 것으로 보지 않는다.
- 일반 JWKS와 access token 검증에 쓰는 공개 키는 마지막 구 키 발급 이후의
  최대 JWT 수명·소비자 clock skew 및 소비자 검증 게이트를 충족한 뒤 공개 종료할
  수 있다. 종료 시각을 계산할 근거가 없으면 계속 공개한다.
- 만료된 ID token hint의 기존 허용 계약을 유지한다. 공개 종료한 키도
  **hint 검증 전용 공개 키**로 보존하며, 일반 JWKS와 access token 검증 목록에서는
  분리한다. 정상 회전에서 hint 공개 키를 자동 삭제하지 않는다.
- 비활성 개인 키는 신규 Pod에 전달하지 않는다. 공개 키 보존을 위해 과거 개인
  키까지 런타임에 남기지 않는다. Vault 이력·백업의 개인 키 폐기는 별도 작업으로
  확인하며, Pod 교체를 비밀 재료의 완전 삭제로 간주하지 않는다.
- 롤백도 이미 발급된 모든 유효 JWT의 공개 키와 hint 검증 이력을 보존한다.
  묶음을 이해하지 못하는 구버전으로의 단순 이미지 롤백은 허용하지 않는다.
- 키 유출에 따른 신뢰 철회는 정상 회전과 다른 사고 대응이다. 유출 키는 hint
  보존 예외로도 남기지 않는다. JWKS에서 삭제해도 외부 소비자 캐시의 신뢰가 즉시
  철회된다고 약속하지 않는다.

개인 키의 진실원천은 기존 Vault 운영 경계다. AuthGate는 Secret을 읽고 검증하며,
Vault나 Kubernetes Secret에 쓰는 권한 또는 원격 키 관리 API를 갖지 않는다.
구체 형식·소비자 게이트·구현 순서는
[구현 설계](../architecture/issuer-signing-key-rotation.md)에 둔다.

## Consequences

기존 로그인·logout hint 동작을 바꾸지 않고 일반 JWKS의 구 키 공개를 끝낼 수 있다.
현재의 2-slot private-key 보조 모델은 active private key와 여러 public key 모델로
바뀌어야 한다. hint 검증 이력은 계속 커지므로 크기 제한과 용량 경고가 필요하며,
한도 도달 시 이력을 조용히 버리는 대신 다음 회전을 중단한다.

키 전환 준비에는 소비자도 포함된다. 특히 브라우저 ID-token 검증과 API Bearer
검증의 캐시는 서로 다를 수 있으므로 서비스 단위의 단일 TTL만으로 판단할 수 없다.
